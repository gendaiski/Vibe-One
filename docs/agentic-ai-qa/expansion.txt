# Model selection and adaptation
## Capability and routing
Basic|What capabilities matter when choosing a model for an agent?|Match the model to the decisions it must make: instruction following, tool selection, structured output, domain knowledge, context handling, and any required image or audio input. Also check available hosting regions, latency, and limits. Evaluate complete tasks with realistic tools; a good conversational answer does not establish reliable action selection.
Intermediate|How do you design a model-routing policy?|Define observable routing signals such as task type, input size, sensitivity, or failure history, then assign eligible models under explicit quality and cost constraints. Test the router and each destination together. Provide a fallback when classification is uncertain, and account for the extra latency and mistakes introduced by routing itself.
Advanced|How do you evaluate a model upgrade without confusing better language with better execution?|Replay representative tasks in resettable environments with comparable budgets, tools, and data. Grade actual final state, permission adherence, tool accuracy, cost, and tail latency. Analyze changed behavior by task slice and use a staged rollout. Preserve the previous model configuration for rollback where the provider supports it.
## Fine-tuning and adaptation
Basic|What is fine-tuning, and when can it help an agent?|Fine-tuning updates a model using training examples to improve behavior on a target distribution. It may help stable output conventions, tool selection, or specialized tasks when good examples exist. It does not automatically supply fresh knowledge or enforce authorization. Start by establishing whether the failure comes from the model rather than missing evidence or broken tools.
Intermediate|When should you use retrieval instead of fine-tuning?|Use retrieval when answers depend on changing documents, user-specific data, or evidence that must be cited and access-controlled. Fine-tuning is more appropriate for repeatable behavior or task patterns, subject to evaluation. They can be combined, but neither repairs poor data quality. Compare approaches using the same held-out user tasks.
Advanced|How do you prevent training data from leaking into agent evaluation?|Keep evaluation cases and close duplicates out of training and example selection. Track dataset lineage, split related cases by source or time where useful, and check for near-duplicates. Use a sealed holdout plus fresh production-derived cases. Report that contamination cannot always be ruled out for externally trained base models.
## Hosting and portability
Basic|What is the difference between hosted and self-hosted models?|Hosted APIs delegate inference operations to a provider. Self-hosting gives an organization more control over deployment, model files, and infrastructure, while making it responsible for capacity, updates, isolation, and security. Neither option is automatically cheaper or private. Compare the complete operational and contractual requirements.
Intermediate|How do you make an agent portable across model providers?|Keep application state and tools behind provider-neutral contracts, then isolate provider-specific message, tool, and streaming adapters. Record capability differences instead of pretending all models support the same features. Maintain contract tests and end-to-end evaluations for each supported model. Portability includes error and refusal handling, not just renaming request fields.
Advanced|How do you plan inference capacity for a self-hosted agent service?|Estimate concurrent requests, prompt lengths, output lengths, and multi-step amplification across typical and worst-case tasks. Load-test batching, queueing, accelerator memory, and token throughput under that distribution. Bound admission and expose backpressure. Include headroom, failure recovery, and model loading time rather than sizing solely from an average tokens-per-second benchmark.
# Knowledge ingestion and retrieval quality
## Ingestion and chunking
Basic|Why does document chunking matter for agents?|Chunking determines which units can be retrieved and whether they contain enough context to support an answer. Chunks that are too small lose meaning; oversized chunks can dilute relevance and waste context. Preserve titles, source links, section relationships, and access metadata. Choose a strategy using actual retrieval tasks rather than one universal chunk size.
Intermediate|How should an agent system process tables and complex documents?|Extract structure alongside text, retaining headers, units, page references, and relationships between cells. Store original artifacts for verification and flag uncertain extraction. Use specialized parsing or visual models when needed, then evaluate numerical and relational accuracy. Flattening a table into unordered text can make a plausible answer materially wrong.
Advanced|How do you keep an index synchronized with changing source documents?|Track stable source IDs, content versions, permissions, and deletion events. Make ingestion idempotent, update affected chunks and indexes, and expose freshness metadata. Reconcile missed events periodically. Test revocation and deletion propagation so removed content cannot continue appearing through stale chunks, caches, or secondary indexes.
## Search and ranking
Basic|What is an embedding in a retrieval system?|An embedding is a numerical representation used to compare items such as text queries and document passages. Similar vectors can indicate related meaning, depending on the embedding model and domain. A high similarity score is not proof that a passage is correct, current, or authorized. Retrieval still needs metadata checks and evidence inspection.
Intermediate|When does hybrid search help?|Hybrid search combines lexical matching with semantic retrieval, helping when a query mixes exact identifiers and conceptual language. Merge or rerank candidates carefully because scores from different systems may not be comparable directly. Evaluate recall and precision on your domain. Exact product codes and rare technical terms often expose weaknesses in semantic-only retrieval.
Advanced|How do you diagnose whether a RAG failure is caused by retrieval or generation?|Check whether relevant authorized evidence exists in the corpus, was indexed correctly, entered the candidate set, survived ranking, and reached the final prompt. If adequate evidence was present but the answer was unsupported, investigate generation and instruction handling. Use stage-specific metrics and labeled cases rather than treating every wrong answer as a model hallucination.
## Grounding and provenance
Basic|What makes a citation useful in an agent answer?|A useful citation points to an accessible source that supports the nearby claim, ideally with a section, passage, or page reference. A real URL alone does not show support. Preserve the source and document version where possible. The reader should be able to distinguish direct evidence from the agent's interpretation.
Intermediate|How should an agent handle conflicting sources?|Compare source authority, publication date, scope, and supporting evidence. Identify whether the apparent conflict is caused by different definitions or time periods. Explain unresolved disagreement instead of silently choosing a convenient statement. For consequential decisions, seek a primary source or escalate when the available evidence is insufficient.
Advanced|How do you evaluate citation faithfulness at scale?|Break answers into factual claims and check whether cited passages actually support each claim, including important qualifiers. Use automated checks for resolvability and calibrated model or human grading for semantic support. Sample by risk and task type. Evaluate unsupported claims separately from missing citations, because perfect citation formatting can still hide fabricated conclusions.
# Memory systems and personalization
## Memory design
Basic|What kinds of information should an agent remember across tasks?|Persist useful, authorized information such as an explicit preference, a validated project convention, or an unresolved task. Keep transient guesses and sensitive material out unless there is a clear purpose and suitable controls. Attach provenance and scope. Memory should improve later decisions rather than become an indiscriminate archive.
Intermediate|How do episodic and semantic memory differ?|Episodic memory records particular events or interactions; semantic memory records generalized facts or concepts. An agent might retain an incident trace as an episode and a verified service limit as a fact. Store the distinction explicitly so a single observation is not promoted into a universal rule without evidence.
Advanced|How do you design memory consolidation without reinforcing false beliefs?|Require provenance, confidence criteria grounded in evidence, and rules for resolving contradictory observations before promoting summaries into persistent facts. Keep original records available for review and support correction. Evaluate recall quality and harmful persistence over repeated sessions. Repeatedly summarizing the same unsupported claim does not increase its truth.
## Recall and freshness
Basic|How does an agent retrieve a saved preference?|The application identifies the authenticated user, searches that user's authorized memory, and inserts relevant preferences into the current context. The model does not automatically remember everything stored in a database. Use stable preference fields where possible, and distinguish an explicit user choice from an inferred tendency.
Intermediate|How do you prevent stale memory from overriding a current instruction?|Give current explicit instructions appropriate precedence, attach timestamps and applicability conditions to stored memory, and revalidate facts that can change. Expire or revise obsolete preferences. When two authoritative instructions conflict and the action depends on the answer, ask for clarification rather than silently trusting an old summary.
Advanced|How do you evaluate long-term memory usefulness?|Run multi-session tasks that require remembering relevant facts while ignoring irrelevant or revoked ones. Measure retrieval precision, task benefit, correction propagation, and cross-user leakage. Include preference changes and contradictory evidence. Compare against a no-memory baseline so storage volume is not mistaken for improved user outcomes.
## Privacy-aware personalization
Basic|What is the difference between a user profile and conversational history?|A profile is a curated set of attributes or preferences intended for reuse. History is a chronological record that may contain temporary, irrelevant, or sensitive information. Deriving a profile is a separate processing decision. Make the purpose and controls clear, and avoid treating every statement in a conversation as a permanent user attribute.
Intermediate|How should users correct agent memory?|Expose the remembered fact or preference and allow a correction or removal to update the authoritative store. Propagate the change to retrieval indexes and dependent summaries, with documented retention behavior for backups. Record provenance without preserving unnecessary sensitive content. Confirm what was changed rather than promising that every historical copy vanished instantly.
Advanced|How can shared organizational memory avoid cross-team data leakage?|Scope each item by identity, tenant, project, and applicable permissions, then enforce those checks before retrieval and at the data service. Recheck permissions after organizational changes. Separate broadly reusable knowledge from restricted source details and test membership transitions. A generated summary of confidential data remains confidential even if it omits the original document title.
# Workflow orchestration and event-driven agents
## Workflow structure
Basic|What is a state machine in an agent application?|A state machine represents valid task states and allowed transitions between them. For example, a purchase may move from draft to reviewed to submitted, with separate failure states. It makes control flow inspectable and restricts invalid jumps. The model can recommend a transition while deterministic code enforces whether it is allowed.
Intermediate|How do you combine deterministic workflow steps with agent decisions?|Keep predictable operations, validation, and authorization in code, and use the model for bounded decisions that require interpretation. Define the input, allowed outputs, and fallback for each model-driven step. Persist transitions and validate invariants. This makes an agent component replaceable without making the entire workflow unpredictable.
Advanced|How do you recover a workflow after its orchestration code changes?|Version workflow definitions and state schemas, then support compatible replay or an explicit migration for in-flight runs. Keep irreversible side effects recorded and avoid rerunning them during migration. Test representative old checkpoints against the new code. Some engines impose replay constraints, so use their actual guarantees rather than assuming arbitrary edits are safe.
## Events and scheduling
Basic|When should an agent wait for an event instead of polling?|Use an event-driven wait when progress depends on an external signal such as a completed payment, user response, or uploaded file. Persist the waiting state and resume when the event arrives. Poll only when events are unavailable or unreliable, with bounded intervals and deadlines. A waiting task does not require repeated model calls.
Intermediate|How do you handle duplicate or out-of-order events?|Give events stable identifiers, deduplicate processing, and use version checks or event sequence information when the source provides it. Make transitions conditional on current state rather than arrival order alone. Reconcile against the source of truth when ordering is uncertain. Record ignored duplicates so operators can explain unexpected delivery patterns.
Advanced|How do you schedule recurring agent work safely?|Define the schedule, timezone, overlap policy, authorization scope, and a budget per run. Use stable run identifiers and prevent unintended concurrent executions. Handle daylight-saving changes, missed schedules, and retries according to explicit rules. Recheck credentials and user intent for ongoing external actions, and provide a clear cancellation mechanism.
## Human checkpoints
Basic|What is a human-in-the-loop checkpoint?|It is a defined pause where a person supplies a decision, correction, or authorization needed for the next step. Save enough state to resume without repeating prior work. Present the concrete artifact or action for review. A checkpoint is useful only if the system respects the decision and ties it to the correct operation.
Intermediate|How do you resume an agent after approval?|Verify the approver's authority, match approval to the exact pending action and version, and confirm that material details have not changed. Record the decision and advance the persisted workflow. Revalidate live constraints before execution where needed. Avoid treating a generic yes from an unrelated conversation as authorization for a different action.
Advanced|How do you design approval expiry and cancellation races?|Represent approval, expiry, cancellation, and execution as competing state transitions governed by atomic checks. Permit execution only from a valid approved state, using the intended operation version. Define what cancellation means once an external system has accepted the action. Return an honest status such as already submitted rather than implying an in-flight side effect can always be undone.
# Distributed execution and reliability engineering
## Delivery semantics
Basic|What does at-least-once delivery mean for agent jobs?|A job can be delivered more than once, especially after worker failures or lost acknowledgements. Consumers must tolerate repeated processing. Use stable job identities and idempotent side effects where possible. A queue's delivery guarantee does not automatically guarantee that an external action occurs only once.
Intermediate|What is an idempotency key and where should it be enforced?|An idempotency key identifies one intended operation across retries. The service executing the write should atomically bind the key to the request and result, rejecting conflicting reuse. Keep keys stable for retries and distinct for genuinely new actions. Client-side memory alone cannot protect against simultaneous workers or a crash.
Advanced|Why is “exactly once” difficult across an agent and an external API?|The application cannot generally atomically commit its local state and an unrelated external side effect. A crash between the two can leave an unknown outcome. Use provider-supported idempotency, transactional outbox patterns, reconciliation, and operation status checks as appropriate. State the scope of any exactly-once claim rather than applying it to the entire distributed system.
## Failure recovery
Basic|What should an agent do when a tool times out?|Treat the result as unknown until the operation's semantics establish otherwise. A read may be safely retried, but a write may already have succeeded. Check operation status or retry using a stable idempotency key. Report uncertainty clearly instead of assuming a timeout means nothing happened.
Intermediate|How do circuit breakers protect agent services?|A circuit breaker temporarily stops calls to a repeatedly failing dependency, reducing wasted work and allowing recovery. Track failures, open the breaker under a defined rule, and probe cautiously before closing it. Combine it with timeouts, backoff, and a useful degraded path. Do not classify user validation failures as dependency outages.
Advanced|How do compensation actions differ from transaction rollback?|Rollback can restore uncommitted changes within a transaction's guarantees. Compensation is a new action that attempts to offset an already completed external effect, such as issuing a refund after a charge. It may fail or leave an audit history and cannot always restore the original situation. Design and authorize compensations explicitly.
## Concurrency and consistency
Basic|Why can parallel agents overwrite each other's work?|Workers can read the same old state and produce competing updates without knowing another change occurred. Shared files and records need ownership or concurrency controls. Partition independent work when possible and merge deliberately. Natural-language instructions to be careful do not prevent a race at the storage layer.
Intermediate|When should you use optimistic concurrency for agent state?|Use versioned updates when conflicts are possible but uncommon and retries are acceptable. Read a version, compute a change, and commit only if the version still matches; otherwise reload and reconsider. Avoid blindly replaying external actions on conflict. The retry must account for any work already completed.
Advanced|How do you maintain invariants across multiple workers and services?|Identify the service that owns each invariant, such as a remaining budget or order status, and enforce atomic state changes there. Use transactions for local invariants and explicit coordination or reconciliation for cross-service processes. Test partitions, retries, and stale reads. A global model conversation is not a substitute for a consistent accounting boundary.
# Agent testing and quality assurance
## Test layers
Basic|What is the difference between unit tests and agent evaluations?|Unit tests check a narrow implementation contract under controlled inputs. Agent evaluations measure behavior across tasks where model choices may vary. Both are useful: a tool's validation can have deterministic tests while the full workflow has repeated outcome evaluations. Passing either layer alone does not establish end-to-end reliability.
Intermediate|What should a tool contract test cover?|Check valid and invalid arguments, permission enforcement, result shape, known errors, timeouts, side effects, and idempotency where relevant. Include the behavior the agent depends on, such as whether a missing record is an empty result or an error. Keep tests focused on the external contract rather than duplicating internal implementation details.
Advanced|How do you test an agent that can change production-like data?|Use an isolated resettable environment with synthetic or appropriately de-identified data and scoped credentials. Record initial and final state, and verify both intended changes and forbidden changes. Replace irreversible external effects with faithful test endpoints where possible. Clearly distinguish simulation success from evidence about live-provider behavior.
## Robustness and adversarial cases
Basic|Why should agent tests include missing or ambiguous information?|Real requests omit fields, use conflicting terminology, or ask for unavailable capabilities. Test whether the agent gathers the right evidence, asks a focused question when necessary, and avoids inventing facts. Define which ambiguities it may reasonably resolve and which block execution. Otherwise a test set rewards confident guesses that fail in use.
Intermediate|What is a metamorphic test for an agent?|It checks an expected relationship between outputs after a controlled input change. For example, reordering irrelevant documents should not change a supported conclusion, while changing an authorized spending limit should change eligible actions. Use domain-valid transformations and explicit expectations. Such tests reveal brittleness without requiring one exact text answer.
Advanced|How do you build a prompt-injection regression suite?|Include attacks through direct input, retrieved content, tool descriptions, and external documents. Vary presentation while testing concrete protected outcomes such as secret access, unauthorized writes, or destination changes. Reset the environment and inspect actual tool actions. Maintain benign lookalike cases so a defense is not rewarded simply for refusing every task.
## Release confidence
Basic|Why should evaluation tasks be versioned?|Versioning preserves the exact cases, environments, and grading rules behind a reported result. Otherwise an apparent improvement may come from an easier dataset or changed labels. Keep old results interpretable and document corrections. Version prompts, tools, and model configuration alongside the evaluation set.
Intermediate|How do you choose regression cases after an incident?|Capture the smallest realistic case that reproduces the failure, then add nearby cases that distinguish the root cause from unrelated behavior. Include the protected outcome and expected recovery. Remove secrets and preserve necessary context. A test that checks only the incident's exact wording may miss the same failure in a slightly different form.
Advanced|How should you make a release decision when eval results conflict?|Prioritize explicit product requirements and risk thresholds, then inspect task slices, sample sizes, and grading reliability. A quality gain may not justify a regression in unauthorized actions or critical users. Seek targeted additional evidence, document accepted tradeoffs, and stage the rollout. Avoid collapsing every dimension into one opaque average score.
# Observability and incident operations
## Traces and diagnostics
Basic|What is an agent trace?|A trace records the steps of a run, such as model calls, tool requests, timing, state transitions, and outcomes. It connects user-visible behavior to execution evidence. Include configuration versions and correlation IDs, while minimizing sensitive payloads. A transcript alone often lacks enough information to diagnose distributed failures.
Intermediate|Which trace fields are useful for debugging tool failures?|Capture the run and operation IDs, tool version, validated argument metadata, authorization result, start and end times, status, retry count, and provider request ID where available. Redact secrets and sensitive contents. Distinguish a transport timeout from a confirmed business rejection so recovery can choose a safe next step.
Advanced|How can observability itself create security risk?|Traces can collect credentials, private documents, user messages, and generated sensitive inferences. Centralizing them broadens exposure and retention. Use redaction, access control, retention limits, and audited retrieval; avoid logging entire payloads by default. Include tracing vendors and exports in the data-governance model rather than treating logs as harmless metadata.
## Service health
Basic|What metrics should an agent dashboard show?|Track successful task completion, failures, escalation, latency, cost, tool errors, and cancellation. Separate user-request volume from model-call volume because each task may have many steps. Show important slices such as model, tenant tier, and task type without exposing private data. Metrics should support decisions, not just count generated tokens.
Intermediate|What is a useful service-level objective for an agent?|An SLO defines a measurable target for a user-relevant outcome over a period, such as a specified share of supported tasks completing within a latency and correctness threshold. Define the eligible population and measurement process carefully. Pair availability with quality and safety indicators because a responsive agent can still produce unusable results.
Advanced|How do you detect a gradual quality regression in production?|Monitor stable task slices, sampled human or calibrated automated reviews, tool-error distributions, and outcome proxies with known limitations. Compare against release versions and control groups where feasible. Watch for changes in user mix and source data. A decrease in complaints alone may reflect lower usage rather than improved quality.
## Incident response
Basic|What should an operator do first during an agent incident?|Contain the affected capability, preserve relevant evidence, assess user impact, and identify whether external side effects continue. Use scoped controls such as disabling a tool or reverting a configuration rather than deleting evidence. Communicate confirmed facts and unknowns. Restoration should include checking task state, not only restarting workers.
Intermediate|How do you investigate an unintended external action?|Correlate the user request, authorization policy, model proposal, actual executed arguments, and downstream result. Determine whether the cause was ambiguous intent, permission failure, injection, retry duplication, or a tool defect. Reconcile affected state and contact appropriate owners through authorized channels. Build the fix around the execution boundary that failed.
Advanced|What makes an agent postmortem actionable?|Document impact, timeline, contributing technical and organizational factors, containment, and the evidence supporting the root-cause analysis. Assign concrete improvements with owners and verification criteria. Include why existing tests or controls did not detect the issue. Avoid attributing everything to the model when tool design, permissions, or recovery behavior amplified the failure.
# Identity, authorization and secrets
## Identity boundaries
Basic|How are authentication and authorization different?|Authentication establishes who is making a request; authorization determines what that identity may do to a resource. An agent may act on behalf of a user, but its tool calls still require resource-level checks. A logged-in session alone is not permission to read every record or perform every action.
Intermediate|What is a confused-deputy problem in an agent system?|A more privileged component may be induced to use its authority on behalf of a less privileged requester. An agent with broad service credentials can become that deputy if tool requests are not bound to the real user's permissions. Enforce the caller's scope at the owning service and avoid allowing prompt text to select a more privileged identity.
Advanced|How do you design delegated authorization for long-running agents?|Bind each run to a verified principal and explicit delegated scope, with expiry, revocation, and auditability. Recheck authority before consequential operations, especially after long waits or membership changes. Use short-lived credentials or brokered access where appropriate. A permission granted when a run started may no longer be valid when it resumes.
## Credential handling
Basic|Why should secrets stay out of agent prompts?|Prompts can be logged, forwarded, included in traces, or exposed through injection and accidental output. Give tools access to credentials through a controlled runtime or secret broker instead. The model typically needs to know a capability exists, not the underlying token. Redaction reduces exposure but does not replace least privilege.
Intermediate|How do you scope credentials for individual tools?|Grant only required operations and resources, separate reads from writes where practical, and bind access to the correct tenant and user context. Use distinct credentials or scoped tokens rather than a global administrator key. Rotate and revoke them through managed mechanisms. Validate that the downstream service actually enforces the requested scope.
Advanced|What should happen when a credential is revoked during a run?|Stop new operations that depend on that credential, record the blocked state, and avoid retries that silently substitute a more privileged identity. Determine whether already submitted external actions completed. Resume only with valid authorization according to the task's rules. Preserve enough state for a clear user explanation and safe continuation.
## Access-policy enforcement
Basic|Where should an agent's permissions be enforced?|Enforce permissions in the runtime and the service that owns the resource, before the operation occurs. Prompts can explain policy but cannot act as the only gate. Validate both operation type and resource scope. A tool that accepts arbitrary tenant IDs must not trust the model to choose only authorized ones.
Intermediate|What is the difference between RBAC and ABAC for agent tools?|Role-based access control grants permissions through roles. Attribute-based access control uses attributes such as user, resource, tenant, time, or workflow state. Systems often combine them. Choose a policy that can express the required constraints and explain decisions. The model can supply task context, but trusted services must determine authoritative attributes.
Advanced|How do you test that an agent cannot cross tenant boundaries?|Create adversarial cases with similar record names, guessed IDs, shared indexes, cached results, and changing memberships. Check retrieval, tools, exports, traces, and memory, not just the UI. Verify denial occurs before sensitive data reaches the model. Use automated policy tests plus end-to-end runs under realistic identities.
# Agent skills, instructions and capability discovery
## Instruction packages
Basic|What is an agent skill or instruction package?|It is a reusable set of task-specific guidance, examples, scripts, or references that an agent can load when relevant. Formats differ across products. A skill can improve consistency but does not inherently grant permission or establish trust. Treat any included executable content and external actions according to the host's security model.
Intermediate|How should an agent decide which skill to load?|Match the skill's declared purpose and prerequisites to the actual task, rather than using a keyword alone. Prefer the narrowest relevant instructions and avoid loading unrelated material into context. Check version and source. If a required skill is unavailable, report the specific gap and continue independent authorized work where possible.
Advanced|How do you defend against malicious or outdated skill packages?|Use trusted distribution, review executable content and external destinations, pin versions where appropriate, and audit updates. Separate descriptive instructions from actual permission grants and enforce access outside the package. Test important workflows after changes. A familiar skill name does not prove that its contents or dependencies remain safe.
## Capability discovery
Basic|Why is tool discovery useful for large agent systems?|It lets the agent obtain relevant tool descriptions without placing every integration in every request. This can reduce context and selection ambiguity. Discovery must be scoped by the user's authorized capabilities. Finding a tool establishes availability, not authorization for every operation it exposes.
Intermediate|How do you evaluate a dynamic tool-discovery system?|Measure whether the necessary tools are retrieved, whether irrelevant or forbidden tools appear, and whether the agent chooses and calls the right contract. Include rare and ambiguous requests plus tools with similar names. Compare total task success, context cost, and latency against a fixed tool set. Discovery errors can masquerade as reasoning failures.
Advanced|How do you manage tool-schema changes without breaking active agents?|Version contracts, preserve compatibility where feasible, and bind active runs to a supported version or migrate explicitly. Validate arguments and expose clear deprecation errors. Update discovery indexes and prompt examples together. Test old checkpoints against changed schemas so a resumed run cannot accidentally reinterpret a parameter or side effect.
## Instruction conflicts
Basic|How should an agent treat instructions found inside retrieved documents?|Treat them as document content unless a trusted mechanism explicitly establishes their authority for the task. A document may describe commands without authorizing execution. Preserve provenance and continue following the actual user request and governing policies. This distinction is central when reading code, emails, web pages, or shared files.
Intermediate|How do you handle conflicting project instructions?|Identify the applicable scope and established precedence, compare the conflicting requirements, and use current task authorization where it resolves the issue. If a consequential decision remains ambiguous, ask a focused question while continuing unaffected work. Record the resolution. Do not silently choose whichever instruction makes execution easiest.
Advanced|How do you evaluate instruction-following across nested contexts?|Construct tasks with trusted instructions, scoped project guidance, and untrusted documents that contain conflicting directives. Grade both the completed task and whether protected boundaries were respected. Vary wording and document placement to prevent rote matching. Inspect tool execution because a compliant final message can conceal an unauthorized action earlier in the run.
# Learning, feedback and optimization
## Feedback signals
Basic|What kinds of feedback can improve an agent system?|Useful signals include verified task outcomes, user corrections, tool errors, expert labels, and well-designed preference comparisons. Each has bias: user satisfaction may reward confidence, and tool success may not mean the user's goal was met. Record provenance and evaluate before using feedback to change behavior.
Intermediate|How do you turn production failures into useful learning data?|Identify the root cause, reconstruct the necessary context, remove sensitive data, and label the correct action or outcome. Include nearby counterexamples so a fix generalizes. Separate tool defects and authorization failures from model behavior that training could change. Keep a held-out evaluation set that is not recycled into tuning.
Advanced|How do you prevent feedback loops from reinforcing bad behavior?|Audit who supplies feedback, what it rewards, and whether the signal correlates with real task success. Track distribution shifts and adversarial manipulation. Require independent evaluation before promoting changes, especially from self-generated labels. A system that judges and trains only on its own confident outputs can amplify errors.
## Reinforcement learning concepts
Basic|What is reinforcement learning in the context of agents?|Reinforcement learning optimizes a policy using feedback about actions and outcomes in an environment. An LLM-based agent may be trained with task rewards or preference-derived signals, but many deployed agents do not learn online at all. Distinguish training the model from changing prompts, memory, or routing during application operation.
Intermediate|What is reward hacking?|Reward hacking occurs when a policy improves the measured reward without meeting the intended objective. For example, an agent might close support tickets quickly while leaving customers unresolved. Use outcome checks, adversarial cases, and multiple measures that expose shortcuts. A more detailed reward is not automatically safe if it still omits important behavior.
Advanced|How would you evaluate a policy optimized for multi-step tool use?|Use environments with independently checked outcomes, explicit action constraints, and held-out tasks that differ from training. Measure total success, unsafe actions, cost, and recovery, not just per-call accuracy. Test whether reward-improving shortcuts exploit simulator artifacts. Assess generalization to realistic tool failures before allowing broader deployment.
## Continuous improvement
Basic|Can an agent improve without changing model weights?|Yes. Better tool contracts, retrieval, instructions, memory selection, validation, and workflow design can improve task success. These changes alter the environment and information available to the model. Measure them with controlled comparisons. Calling the improvement learning should not obscure whether the model itself was actually updated.
Intermediate|How do you prioritize agent improvements?|Group failures by frequency, impact, and root cause, then estimate the expected benefit and effort of each change. Fix deterministic defects and broken permissions before adding more reasoning loops. Use a representative baseline and a small experiment to validate the intervention. Track cost per successful task as well as accuracy.
Advanced|How do you govern automatic prompt or policy optimization?|Limit the search space, use approved training data, and evaluate candidates against held-out quality and policy criteria. Version every candidate and require appropriate review before production promotion. Keep rollback available and prevent optimizers from modifying their own evaluation controls. Improvement in one metric is insufficient evidence for unrestricted self-modification.
# Coding agents and software engineering
## Repository understanding
Basic|What should a coding agent inspect before changing a repository?|Read applicable project instructions, locate the relevant implementation, and understand the current behavior and local conventions. Inspect the working tree so existing user changes are preserved. Identify how the change can be verified. Avoid reading unrelated secrets or assuming the repository is clean.
Intermediate|How do you give a coding agent a useful task specification?|State the observed problem, expected behavior, scope, constraints, and acceptance evidence. Include a concrete failing scenario or reproduction when available. Let the agent resolve routine implementation details within that scope. A specification should explain the user outcome rather than prescribe every edit without understanding dependencies.
Advanced|How should a coding agent manage changes in a shared workspace?|Inspect current changes, give one owner to each overlapping file or region, and coordinate integration explicitly. Avoid resetting or overwriting work the agent did not create. Use isolated branches or worktrees when appropriate and verify the integrated result. Independent tasks are easier to parallelize than multiple agents rewriting the same core module.
## Implementation and verification
Basic|Why is a compiling program not enough evidence of a successful agent change?|Compilation checks syntax and some type constraints, but the feature can still violate requirements, break a user flow, or mishandle data. Verify behavior appropriate to the change and inspect the diff. For visible interfaces, review the rendered result. Report any verification limits clearly.
Intermediate|How should a coding agent choose which tests to run?|Select checks that cover the changed behavior and likely regressions, following applicable project requirements. Prefer meaningful existing tests and focused manual or integration checks when appropriate. Broaden testing if failures or unresolved risk justify it. Avoid writing trivial tests that simply repeat the implementation without checking a useful contract.
Advanced|How do you evaluate a coding agent on real maintenance work?|Use representative tasks with hidden acceptance checks, realistic repository state, and constraints on unrelated changes. Grade functional behavior, regression risk, maintainability, and whether the agent preserved user work. Track tool use, time, and cost. Prevent evaluation leakage from issue answers or reference patches where possible.
## Delivery and review
Basic|What should an agent include in its change report?|Explain what changed, why it matters, how it was verified, and any material limitations. Link the relevant artifacts or files and avoid claiming tests ran when they did not. The report should let a reviewer assess the result without reading the entire interaction history.
Intermediate|How should a coding agent prepare a reviewable pull request?|Keep the final scope coherent, inspect the diff, complete relevant checks, and write a description around the concrete problem and resulting behavior. Include validation and meaningful risks. Follow the repository's contribution process and task authorization. A draft pull request can make work reviewable without implying production deployment approval.
Advanced|How do you prevent a coding agent from treating deployment as a harmless final step?|Model deployment, migrations, secret changes, and destructive operations as explicit capabilities governed by authorization and environment policy. Separate preparation from execution and present concrete artifacts for review when approval is required. Enforce controls in deployment tooling. A successful local test does not authorize a production change.
# Research, analysis and knowledge-work agents
## Research design
Basic|How should a research agent scope a broad question?|Identify the decision or learning goal, key subquestions, relevant time period, and constraints on sources or depth. Start with a manageable evidence plan and adjust it when sources reveal gaps. If scope remains ambiguous, state assumptions or ask a focused question. More searches are not automatically better research.
Intermediate|How do you avoid citation laundering in agent research?|Check the underlying primary evidence rather than citing one article that repeats another unsupported claim. Track whether a source reports firsthand findings or summarizes someone else. Attach citations to the claims they actually support. If the original source is unavailable, explain that limitation instead of presenting secondary reporting as direct verification.
Advanced|How do you evaluate a research agent on an open-ended task?|Define a rubric for coverage, source authority, factual support, uncertainty handling, and usefulness for the user's decision. Use expert review and calibrated automated checks where appropriate. Judge the evidence trail and final synthesis rather than the number of searches. Include tasks with contradictory sources and questions that cannot be resolved from available evidence.
## Data analysis
Basic|When should an agent use code for analysis?|Use code for reproducible calculations, data transformations, statistical analysis, and plots when the task benefits from exact execution. Inspect the data schema and units first. Validate results against simple checks and explain assumptions. A language-model estimate should not replace a calculation that can be executed reliably.
Intermediate|How do you prevent a data-analysis agent from making unsupported causal claims?|Distinguish descriptive patterns, predictive associations, and causal effects. Check study design, confounders, selection bias, and whether an intervention or identification strategy supports causality. Present uncertainty and alternative explanations. Running a regression alone does not establish that changing one variable will cause the predicted outcome.
Advanced|How do you build a reproducible analysis workflow for an agent?|Version input references, code, dependencies, random seeds where relevant, and analysis choices. Save intermediate artifacts and a clear execution path. Use isolated compute with scoped data access and record validation checks. Reproducibility should include the interpretation and assumptions, not only rerunning a notebook to produce the same chart.
## Writing and synthesis
Basic|How should a writing agent preserve factual accuracy?|Separate source-supported facts from stylistic choices and original inference. Keep evidence references for factual claims and flag missing information rather than inventing it. Review names, numbers, quotations, and dates carefully. A polished sentence can still be factually wrong.
Intermediate|How do you coordinate research and writing agents?|Define an evidence handoff containing claims, sources, uncertainty, and unresolved questions before drafting. Give the writer authority to improve presentation without silently changing factual meaning. Review the final text against the evidence. Separate roles help only when their contracts prevent unsupported additions during synthesis.
Advanced|How do you evaluate an agent-generated briefing for decision makers?|Check whether it answers the actual decision question, presents relevant options and tradeoffs, supports claims, and distinguishes uncertainty. Assess omissions that could change the decision, not just factual errors in included text. Use domain reviewers for consequential topics. Concision is valuable when it preserves the information needed to act responsibly.
# Business operations and transactional agents
## Customer support and CRM
Basic|What tasks are suitable for a customer-support agent?|Agents can classify requests, retrieve authorized account information, draft responses, and guide users through supported processes. Higher-consequence changes need independent policy and permission checks. Define escalation conditions and verify resolution. A fast response is not the same as a solved customer problem.
Intermediate|How do you stop an agent from inventing company policy?|Retrieve the applicable current policy from an authorized source and require explanations to stay within it. Use deterministic checks for rules that control transactions. If a case falls outside policy, escalate rather than improvise commitments. Track policy versions so a response can be audited later.
Advanced|How do you evaluate a support agent beyond ticket deflection?|Measure verified resolution, repeat contacts, escalation appropriateness, policy adherence, and customer impact alongside cost and response time. Audit difficult and sensitive cases separately. Ticket closure can be gamed or misinterpreted. Use a baseline and controlled rollout where feasible to estimate the feature's real effect.
## Sales and scheduling
Basic|How can an agent help with scheduling without creating confusion?|Collect constraints, inspect authorized calendar availability, propose clear options with timezones, and distinguish tentative holds from confirmed events. Verify participants and meeting details before writes. Record the event result. Treat cancellations and rescheduling as separate actions with their own consequences.
Intermediate|What controls matter for an outbound sales agent?|Respect authorized audience, consent and applicable communication rules, approved claims, frequency limits, and opt-outs. Keep generated personalization grounded in permitted data. Review or constrain sending according to policy and user authorization. Draft quality does not justify unrestricted messaging at scale.
Advanced|How do you prevent repeated outreach across multiple agent workflows?|Use a shared contact and campaign ledger with stable identifiers, atomic send eligibility checks, and provider message reconciliation. Deduplicate retries and coordinate frequency limits across teams. Recheck opt-out state at send time. A per-agent local memory cannot enforce organization-wide contact policies.
## Payments and orders
Basic|Why should payment confirmation come from a payment system?|A UI success screen or model statement can be wrong or fabricated. Confirm payment using authenticated provider events or status checks and the matching order, amount, and currency. Handle pending or unknown states explicitly. Do not treat a demo button as evidence of a real charge.
Intermediate|How should an agent manage a partially completed order?|Persist which steps succeeded and which remain pending, then reconcile external states before retrying. Inform the user of the actual status and available next actions. Use idempotent operations for payment and submission. Avoid starting a second order merely because the first run lost its response.
Advanced|How do you design an agent that can purchase within a budget?|Enforce identity, allowed vendors, item constraints, spend limits, and required approvals outside the model. Reserve budget atomically before submission and reconcile actual charges. Present material purchase details for review when required. Include taxes, shipping, duplicate retries, and cancellations in the accounting model.
# Agent platforms and developer experience
## Platform building blocks
Basic|What core services does an agent platform need?|Typical building blocks include identity, run orchestration, model access, tool execution, persistent state, evaluation, observability, and configuration management. Add only what the product needs. Define boundaries so applications do not each recreate security and recovery logic inconsistently.
Intermediate|How do you design a reusable tool gateway?|Authenticate callers, scope available tools, validate contracts, enforce authorization, and correlate execution with run IDs. Provide consistent error semantics, deadlines, and audit events. Keep domain business rules in the owning service. A gateway should not become a universal administrator bypass simply because every agent uses it.
Advanced|How do you manage backwards compatibility for a shared agent platform?|Version APIs, state formats, tool contracts, and supported model adapters. Define deprecation and migration policies for applications and in-flight runs. Use contract tests and staged releases with representative clients. Platform changes can affect many agents at once, so blast radius and rollback deserve explicit planning.
## Developer workflows
Basic|What should a local agent development environment provide?|Provide safe test credentials or mocks, inspectable traces, representative data, configurable models, and a way to reset state. Make consequential external actions clearly distinct from simulation. Keep setup reproducible and document required permissions. A local demo should not accidentally operate on production resources.
Intermediate|How do you make agent debugging practical for application teams?|Expose correlated traces, deterministic tool replays where possible, versioned configurations, and compact failure summaries. Let developers inspect relevant state without revealing unnecessary sensitive content. Provide fixtures for common failures and a way to reproduce a run in isolation. A single final model response rarely explains a multi-step defect.
Advanced|How should an agent platform support cost attribution?|Associate model calls, tools, storage, and execution resources with run, tenant, application, and configuration identifiers. Reconcile estimated with actual billed usage and account for retries and background work. Expose cost per successful task as well as raw spend. Avoid double-counting shared infrastructure allocations as if they were direct provider charges.
## Isolation and deployment
Basic|Why separate the control plane from the execution plane?|The control plane manages configuration, identity, and policy; the execution plane performs runs and tool work. Separation can improve security, scaling, and operational clarity. Define trusted communication between them and avoid giving workers unrestricted configuration authority. The exact split should match the platform's complexity.
Intermediate|How do you isolate tenants in an agent execution service?|Scope credentials, data, storage, queues, and resource limits to the correct tenant. Use appropriate process or compute isolation and enforce access at service boundaries. Include logs and caches in the isolation model. A tenant label in a prompt is not a technical boundary.
Advanced|How do you design regional or data-residency controls for agents?|Map where model inference, tools, retrieval, memory, traces, backups, and support access process data. Route only to services that meet the applicable contractual and legal requirements. Enforce region policy in infrastructure and service configuration. Keeping the database in one region is insufficient if prompts or traces are exported elsewhere.
# Edge, robotics and embodied agents
## Physical-world interaction
Basic|What makes an embodied agent different from a text-only agent?|An embodied agent acts through a physical system such as a robot and receives observations from sensors. Actions can have immediate real-world consequences, and perception is noisy and incomplete. Use explicit control and safety layers appropriate to the hardware. A fluent language plan is not a verified motion command.
Intermediate|How should language planning connect to robot control?|Translate high-level goals into bounded capabilities with validated preconditions and feedback from the physical state. Keep fast control loops and safety constraints in suitable deterministic or specialized controllers. Replan when observations invalidate assumptions. The language model should not directly bypass collision limits or emergency-stop mechanisms.
Advanced|How do you evaluate transfer from simulation to a real robot?|Test variation in sensing, dynamics, object properties, timing, and environment conditions, then validate incrementally on hardware under controlled constraints. Measure success and unsafe behavior separately. Simulation coverage reduces risk but cannot prove physical performance. Keep emergency intervention and clear operating limits during real-world evaluation.
## Edge deployment
Basic|Why might an agent run at the edge?|Local execution can reduce network dependence, improve response time, and limit which data leaves a device. It also faces memory, compute, power, and update constraints. Decide which tasks truly need local inference and which can use approved remote services. Edge deployment does not automatically guarantee privacy.
Intermediate|How do you split work between a device and a cloud agent?|Place latency-critical or sensitive processing locally when appropriate and send only permitted information to remote capabilities. Define behavior when connectivity is unavailable and reconcile state on reconnection. Keep authorization and version compatibility explicit. A hybrid design should degrade predictably rather than silently abandoning local safety checks.
Advanced|How do you update a fleet of edge agents reliably?|Use authenticated versioned packages, staged rollout, compatibility checks, and rollback or recovery paths appropriate to the device. Track hardware variation, offline periods, and partially applied updates. Separate model and policy changes when necessary. Evaluate the complete fleet state, not just whether one connected test device accepted the update.
## Uncertainty and safety
Basic|Why does sensor uncertainty matter for agent actions?|A system may misidentify an object, location, or person, making an otherwise valid action inappropriate. Preserve uncertainty and require additional observation when confidence is insufficient for the action. Use constraints tied to real physical risk. Do not interpret a model's confident wording as calibrated sensor certainty.
Intermediate|What is a safe fallback for an embodied agent?|A fallback is a predefined behavior that reduces risk when perception, planning, or connectivity fails, such as stopping motion or handing control to an operator. The correct behavior depends on the system and environment. Implement it in the control stack and test triggering conditions. A language instruction to be safe is insufficient.
Advanced|How do you define operating boundaries for a physical agent?|Specify permitted environments, speeds, loads, users, sensor conditions, and task classes using the relevant engineering and regulatory process. Monitor for conditions outside those limits and transition to a validated fallback. Validate changes before expanding scope. Success in one workspace does not establish suitability for a different physical environment.
# Economics, capacity and product strategy
## Unit economics
Basic|What is cost per successful task?|It is the total attributable cost of attempting tasks divided by the number that meet a defined success criterion. Include failed attempts, retries, tool fees, and relevant execution costs. Specify the measurement period and task population. Cheap individual model calls can still produce an expensive service when many steps fail or repeat.
Intermediate|How do you estimate the cost of a new agent feature?|Model task volume, calls per task, input and output lengths, tool usage, retries, and execution resources under realistic distributions. Include evaluation and operational overhead appropriate to the estimate. Validate assumptions with a small pilot. Report ranges rather than a single precise number derived from idealized prompts.
Advanced|How do you choose between more model compute and stronger product constraints?|Compare the improvement in task success against cost, latency, user friction, and risk. A constrained form or deterministic validation may resolve ambiguity more effectively than extra reasoning calls. Test alternatives under the same outcome criteria. Product design can change the problem rather than forcing the model to solve an unnecessarily broad one.
## Capacity and demand
Basic|Why is registered-user count a weak capacity estimate?|Only some users are active at once, and different tasks create very different model and tool loads. Capacity depends on peak concurrency, request distribution, run duration, and downstream limits. Measure those quantities and include burst behavior. A million accounts does not imply a million simultaneous agent runs.
Intermediate|How do you handle fairness between heavy and light users?|Apply tenant or user quotas, weighted scheduling where appropriate, and concurrency limits that prevent long runs from monopolizing capacity. Make admission and cancellation behavior predictable. Measure waiting time by user segment. Fairness policy should reflect the product's commitments rather than emerge accidentally from queue ordering.
Advanced|How do you plan for cascading overload in a multi-step agent platform?|Model how retries and fan-out amplify demand across providers and tools. Use backpressure, bounded queues, deadlines, per-dependency concurrency limits, and load shedding. Test partial outages and recovery rather than only steady-state throughput. A degraded dependency should not trigger unlimited parallel retries that exhaust the rest of the platform.
## Product fit
Basic|How do you decide whether a task should become an agent feature?|Identify a recurring user problem, the required access, a measurable outcome, and why a simpler interface or workflow is insufficient. Estimate operational cost and consequences of failure. Validate with real users and a bounded prototype. Agent autonomy is a design choice, not a product benefit by itself.
Intermediate|How do you measure an agent's value to users?|Measure task completion, saved effort, quality, trust, and user control using appropriate baselines and research methods. Track abandonment and corrections alongside adoption. Distinguish novelty-driven use from sustained utility. A feature can generate many interactions while creating more review work than it saves.
Advanced|When should you reduce an agent's scope after launch?|Reduce scope when evidence shows repeated failures, unacceptable intervention cost, poor economics, or risk outside the supported operating conditions. Identify which task slices still provide value and constrain access accordingly. Communicate supported behavior clearly and evaluate the narrower system. Fewer capabilities can produce a more dependable product.
# Open standards and agent interoperability
## Protocol boundaries
Basic|How is agent-to-agent communication different from tool calling?|Tool calling usually requests a defined operation from a capability. Agent-to-agent communication can delegate a broader task with progress, negotiation, or artifacts. Boundaries vary by implementation. In both cases, define identity, permissions, schemas, timeouts, and completion criteria rather than relying on informal conversation alone.
Intermediate|What should an inter-agent task contract contain?|Include the goal, authorized scope, inputs, expected outputs, deadlines, budget, status model, artifact format, and cancellation behavior. Specify which party owns external side effects and how failures are reported. Avoid assuming both agents share hidden conversation context. Explicit contracts make integration and evaluation possible.
Advanced|How do you establish trust between independently operated agents?|Authenticate services, verify the delegating identity and permitted scope, validate artifacts, and enforce policy at every receiving boundary. Limit transitive delegation and audit consequential actions. A protocol handshake proves compatibility or identity only within its guarantees; it does not establish that another agent's reasoning or evidence is correct.
## Artifacts and schemas
Basic|Why should agents exchange structured artifacts?|Structured artifacts define fields and status explicitly, reducing ambiguity in handoffs and allowing validation. Examples include a research evidence bundle or a code-change report. Preserve references to original sources and distinguish unknown from absent data. Human-readable summaries remain useful but should not be the only machine contract for important workflows.
Intermediate|How do you evolve schemas used by multiple agents?|Use version identifiers, backward-compatible additions where feasible, and explicit migrations for breaking changes. Define required fields and unknown-field behavior. Validate both producers and consumers with shared contract tests. Do not silently change the meaning of an existing field while retaining its name.
Advanced|How do you preserve provenance across a chain of delegations?|Carry stable task, source, and artifact identifiers with timestamps, authorship or service identity, and transformations performed. Preserve links to supporting evidence and permission scope. Validate provenance claims where they affect trust. A final summary should not erase which parts were observed, inferred, or supplied by an untrusted participant.
## Interoperability operations
Basic|What is capability negotiation between agent systems?|It is a process for discovering which features, versions, and operations each participant supports. Use the negotiated result to select compatible behavior and reject unsupported requests clearly. Discovery should be permission-scoped. Advertising a capability does not mean every caller is authorized to use it.
Intermediate|How do you handle cancellation across delegated agents?|Define a cancellation identifier and state transition, propagate the request to active workers, and report which operations stopped versus already completed. Use deadlines and cleanup rules for abandoned work. Cancellation is best-effort for external actions already accepted by another service, so reconcile results rather than promising universal rollback.
Advanced|How do you test interoperability without assuming one vendor's behavior?|Build protocol conformance and contract tests covering schemas, version negotiation, errors, timeouts, retries, cancellation, and permission denial. Run against multiple independent implementations when possible. Include malformed and unexpected inputs. Successful message exchange is only the first step; verify end-to-end task state and protected boundaries.
# Advanced architecture and frontier concepts
## World models and simulation
Basic|What is a world model in an agent discussion?|The term often refers to a representation that predicts aspects of an environment and how actions may change it. It may be learned or explicitly coded, and usage varies across research and products. Distinguish a model's plausible imagined outcome from an observed external result. Define the term before making capability claims.
Intermediate|How can simulation help an agent choose actions?|A simulator can estimate candidate outcomes under specified assumptions, helping compare plans before execution. Validate how well it represents the real task and account for uncertainty. Keep simulated actions separate from real operations. A plan that succeeds in an inaccurate simulator may fail systematically in deployment.
Advanced|How do you prevent an agent from exploiting simulator weaknesses?|Use held-out environments, varied dynamics, independent outcome checks, and tests outside the optimization simulator. Inspect suspicious shortcuts and compare predicted with observed real-world behavior. Limit deployment based on evidence about transfer. High simulation reward alone is insufficient for a claim of general real-world competence.
## Search and deliberation
Basic|What is planning search in an agent system?|Planning search explores alternative action sequences or candidate solutions before choosing one. It can be implemented with code, model calls, or both. Search is useful only if candidates can be evaluated meaningfully. Bound compute and compare against a simpler direct approach.
Intermediate|When can extra deliberation make an agent worse?|It can add latency, cost, contradictory assumptions, and opportunities to overfit a flawed evaluator. A correct simple answer may be revised into an incorrect elaborate one. Use stopping criteria and evidence-based evaluation. More tokens or critique rounds should earn their place through measured task improvements.
Advanced|How do you compare search-based planning with reactive agent loops?|Evaluate both on tasks with varying horizon, observability, and recovery cost, under comparable total budgets. Measure successful outcomes, constraint violations, compute, and adaptation to unexpected events. Search may help when future consequences can be modeled; reactive loops may suit rapidly changing conditions. Avoid declaring one architecture universally superior.
## Self-modification and scope
Basic|What is the difference between self-reflection and self-modification?|Self-reflection produces feedback or revised output within a run. Self-modification changes persistent instructions, code, tools, or model parameters. The latter can affect future tasks and needs explicit controls. A generated suggestion to improve a system is not evidence that a safe improvement was applied.
Intermediate|How should an agent propose changes to its own tools?|Produce a reviewable patch or specification, explain the observed problem, and include validation evidence. Test changes in an isolated environment before promotion. Preserve permission boundaries and version compatibility. The agent proposing a change should not automatically gain authority to weaken the controls that evaluate or authorize it.
Advanced|How do you evaluate claims of general-purpose autonomous agents?|Ask for a defined task distribution, operating constraints, failure reporting, intervention rates, and independent outcome checks. Examine contamination, hidden human assistance, and selection of demonstrations. Compare against baselines under equal budgets. Broad marketing language does not establish reliable performance across unseen tasks and environments.
